Период: 11 апреля 2026 - 17 апреля 2026.

На этой неделе я упростил подготовку PostgreSQL для работы с Voryn и сделал еще один шаг к более цельному публичному API.

Раньше схема базы данных применялась через отдельную CLI-команду. Это удобно для быстрого старта, но плохо встраивается в реальные проекты, где уже есть свои миграции, скрипты развертывания и CI/CD.

Что изменилось:

- убрал отдельную CLI-команду инициализации;
- добавил функцию для применения SQL-файла к PostgreSQL;
- добавил проверку наличия обязательных таблиц Voryn;
- экспортировал новые функции из публичного API библиотеки;
- перенес workerId fetch worker в общую конфигурацию.

Главное изменение недели - схема PostgreSQL перестала быть привязана к одному способу запуска.

Теперь пользователь может применить SQL самостоятельно через миграции, psql или CI/CD. Если нужен готовый вариант, библиотека предоставляет небольшую функцию, которая читает SQL-файл, выполняет его и пишет результат в лог.

Рядом появилась и функция проверки схемы. Она проверяет, что в базе существуют таблицы, необходимые для работы pipeline. Это позволяет обнаружить проблему при запуске, а не после того, как один из воркеров уже начал обрабатывать данные.

Я также перенес workerId fetch worker в его конфигурацию. Изменение небольшое, но делает создание воркера последовательнее: все параметры, которые описывают его поведение и идентичность, теперь находятся в одном месте.

Эта неделя была про встраиваемость. Библиотека не должна диктовать приложению, как управлять базой данных. Она должна давать понятные строительные блоки, которые можно встроить в существующую инфраструктуру.

В следующем посте расскажу, как проверка схемы стала частью создания воркеров и как начал формироваться более удобный API для их запуска.
